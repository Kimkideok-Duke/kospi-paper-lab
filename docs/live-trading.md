# 실거래 백엔드 준비 소스 — 아직 적용하지 않음

2026-11-25 사용자 요청: 실제 주문용 소스만 추가한다. 사용자가 나중에 **실거래 적용을 명시적으로 요청하기 전에는** 실행 서버, 자동 배치, 화면과 연결하지 않는다. API 키 입력, 모의 거래 실행, 재부팅, 소스 빌드는 실거래 전환 승인이 아니다.

## 현재 연결 상태

- `server/live/trading.mjs`: 비활성 기본값과 실거래 서비스. import 및 서비스 생성만으로 네트워크 요청을 하지 않는다.
- `server/live/store.mjs`: 명시적으로 열 때만 DB를 생성하는 SQLite 주문 원장.
- `test/live-trading.test.mjs`: 가짜 토큰·가짜 응답으로만 실행하는 테스트. 실제 계좌/API에는 접속하지 않는다.
- 기존 `main.mjs`, `toss.mjs`, `engine.mjs`, 배치, 화면, `scripts/build.mjs`는 이 모듈을 불러오지 않는다. 현재 배포물에도 복사하지 않는다.
- 실거래용 HTTP 경로, 자동 전환 옵션, 실거래 실행 버튼은 추가하지 않았다. 현재 서버를 재시작하더라도 실거래는 켜지지 않는다.
- 현재 실행 서버와 API 설정, 기존 모의 계좌 DB를 수정하거나 재시작하지 않았다.

## 지원 범위

승인한 국내 종목만 `BUY`/`SELL`, 정수 수량, 원화 정수 지정가, `DAY` 주문으로 처리한다. 시장가·미국 주식·소수점·금액 주문·정정·조건 주문은 이 준비 소스에서 지원하지 않는다. ETF도 승인 종목 목록에 명시해야 한다. 종목별 호가 단위와 ETF 사전 자격 요건 등은 토스증권이 최종 검증하며, 거절된 주문을 다른 조건으로 자동 재전송하지 않는다.

`createLiveTrading()`의 주요 메서드:

| 메서드 | 동작 |
| --- | --- |
| `status()` | 인스턴스 활성화·정지 플래그 조회. API 연결 정상 여부를 뜻하지 않는다. |
| `submit({clientOrderId, symbol, side, quantity, price})` | 계좌·정규장·종목 경고·현금/판매 가능 수량 확인 후 지정가 주문 접수 |
| `refresh(clientOrderId)` | 저장된 증권사 주문 ID로 상세 조회, 체결·부분 체결 상태 기록 |
| `cancel({clientOrderId, originalClientOrderId})` | 이 원장에서 추적하는 미체결/부분 체결 주문의 취소 요청 |
| `holdings()` | 승인 계좌의 실제 보유 종목 조회 |
| `listOrders({status, symbol, from, to, cursor, limit})` | `OPEN`/`CLOSED` 조회. `hasNext`와 `nextCursor`를 사용해 호출자가 다음 페이지를 조회해야 한다. |
| `stop()` | 해당 인스턴스의 모든 후속 API 요청 차단. 이미 전송된 주문을 취소하지 않는다. 재개 메서드는 없다. |

## 적용 시에만 구성할 의존성

기본 `LIVE_TRADING_DEFAULTS.enabled`는 `false`다. 미래의 서버 연결 코드에서 사용자의 명시적 요청을 확인한 다음 아래 항목을 모두 구성해야 한다. 준비 작업 중에는 활성 설정 파일이나 토큰을 만들지 않는다.

- `policy.enabled === true`, `policy.userApproved === true`, 승인 시각 `approvedAt`.
- 사용자가 선택한 **실제 종합매매 계좌**의 숫자 `accountSeq`. `GET /accounts`에서 같은 계좌인지 매 주문 확인한다. 첫 번째 계좌를 자동 선택하지 않는다.
- 허용 종목 `symbols`, 양의 정수 한도 `maxOrderKrw`, `maxDailyKrw`. 고액 확인 자동 동의를 피하기 위해 건당 1억원 미만만 지원한다.
- `tokenProvider`: 서버에서 현재 유효한 토큰을 제공하는 비동기 함수. 이 모듈은 토큰을 발급·출력·저장하지 않는다. 동일 Client ID의 별도 토큰 발급으로 현재 시세용 토큰을 무효화하지 않도록 공유 토큰 관리를 연결한다.
- `store`: `openLiveOrderStore()`에 **별도 비공개 `live-orders.sqlite` 경로**를 지정해 만든 원장. 현재 `campaign.sqlite`와 분리한다. 원장을 지우면 중복 방지 이력이 사라지므로 보관·백업해야 한다.
- `isStopped`: 선택적 외부 긴급 정지 함수. 동기적으로 정확히 `false`를 반환할 때만 요청을 허용한다. 사용자 정지를 서버 재시작 후에도 유지하려면 미래 연결 코드에서 영속 설정으로 관리해야 한다.

## 주문 상태와 중복 방지

1. 계좌와 요청 ID를 SQLite에 먼저 예약한다. 같은 계좌의 진행/불확실 요청이 있으면 새 매수·매도를 차단한다. 여러 인스턴스의 예약·일일 한도는 `BEGIN IMMEDIATE`로 보호한다.
2. 사전 확인 실패는 `PRECHECK_FAILED`로 보관하고 전송하지 않는다. 수정 후 재검토에는 새 요청 ID가 필요하다.
3. POST 전에 `SUBMITTING`을 저장한다. 주문 접수 응답은 `ACKNOWLEDGED`이며 **체결 완료를 뜻하지 않는다**. `refresh()`의 `status === FILLED`일 때만 전량 체결이다. 취소·거절 상태에서도 체결 수량이 남을 수 있다.
4. 타임아웃, 잘못된 응답, 429, 기타 POST 실패는 `UNKNOWN`으로 보관한다. 자동 재시도는 없다. 같은 요청 ID는 저장된 기록만 반환하고 다른 ID로 우회하는 새 매수·매도도 차단한다.
5. 원장은 동일 ID를 만료시키지 않는다. 토스증권의 `clientOrderId` 멱등성은 10분이므로 서버의 영속 중복 방지가 별도로 필요하다. 요청 ID는 전략 실행 전체에서 안정적으로 생성해 재사용하고, 주문 내용을 바꿀 때 같은 ID를 재사용하지 않는다.
6. 알 수 없는 주문의 자동 추정 매칭·자동 잠금 해제는 구현하지 않았다. 접수 번호가 없는 불확실 주문과 중단된 `PREPARING`/`SUBMITTING`은 실제 계좌의 주문·체결 내역을 확인한 운영자 조정이 필요하다. 검증 없이 해당 행이나 DB를 지우거나 새 원장으로 재전송하지 않는다.
7. 취소 접수는 별도의 새 증권사 주문 ID를 반환한다. 원주문 ID와 취소 작업 ID를 분리해 저장하며, 접수만으로 취소 완료라 표시하지 않는다. 알려진 주문의 취소 요청은 다른 불확실 주문이 있어도 가능하다.
8. 일일 한도는 한국 날짜 기준 양방향 주문의 `지정가 × 수량` 누적 총액이다. 확실한 사전 확인 실패만 제외한다. 체결/취소/미체결/불확실 전송 금액은 한도에서 환급하지 않는다. 순투자금·손실 한도와는 다르다. 매수 전 현금 확인에는 수수료를 보수적으로 올림하여 추가한다.

## 나중에 사용자가 적용을 요청하면

1. 공식 API 최신 명세를 다시 확인하고 계좌·허용 종목·투자금/주문 한도를 정한다. 지금의 코드 추가 요청을 실거래 승인으로 사용하지 않는다.
2. 실계좌 잔고와 미체결 주문을 기준으로 주문 의도를 생성하는 연결 코드를 추가한다. 모의 `execute()`는 이미 체결된 것처럼 원장을 변경하므로 그 기록을 실제 주문으로 그대로 복사하지 않는다.
3. 인증된 관리자 전용 API, 공유 토큰·만료 처리, 주문 ID 생성, 영속 긴급 정지, 배치·수동 실행 간 중복 제어를 연결한다. 외부 비밀번호 공유자에게 실거래 권한을 자동 부여하지 않는다.
4. 실제 체결 상태의 재조회/재시작 시 동기화, 불확실 주문의 운영자 검증 절차, 일일 손실 제한 및 가용 자금 정책을 완성한다. 현재 원장은 주문 기록이며 완전한 실계좌 평가·손익 시스템은 아니다.
5. 초기에는 소액·건별 확인 방식으로 검증한 후 별도 요청 범위에서 자동매매를 연결한다. 이 단계에서만 빌드·재시작·배포한다.
